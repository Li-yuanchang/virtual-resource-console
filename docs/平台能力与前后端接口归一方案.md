# 平台能力与前后端接口归一方案

## 1. 背景与目标

VRC 同时接入 XenServer、VMware、Proxmox VE 和 KVM/libvirt。平台差异必须由 API 层的 Provider、策略和适配器吸收，Web 前端只消费稳定 DTO，不得通过散落的 `providerType if/else` 判断业务能力、解析平台原始标识或推导任务终态。

本方案解决以下问题：

- 前端自行判断改名、扩容、控制台、ISO、网络探测等能力。
- 创建页面和后端各自生成、校验创建计划，形成两套业务口径。
- 创建请求同时传模板 ID、模板派生字段和完整计划，参数重复且可能冲突。
- 前端解析 VMware MOID、PVE `node:vmid`、XenServer 磁盘设备等原始字段。
- 工作流步骤、进度和阻断状态在前后端重复维护。
- 平台名称、默认端口、网络术语散落在多个文件。

## 2. 职责边界

### 2.1 API 层负责

- 根据连接解析真实 `providerType`，不能信任客户端重复提交的平台类型。
- 通过 Provider Registry 选择平台实现。
- 返回平台能力、操作约束、默认端口和用户可见原因。
- 生成并校验创建计划，返回结构化阻断项和提示项。
- 解析平台原始资源标识，输出统一控制台引用、磁盘描述和资源状态。
- 维护任务步骤、进度、终态、就绪状态和错误码。

### 2.2 Web 前端负责

- 收集用户意图和覆盖值，不推导平台执行规则。
- 根据 API 返回的 `supported`、`reasonCode`、`constraints` 控制交互。
- 直接渲染后端任务步骤和进度。
- 将统一状态映射为颜色、图标和布局。
- 平台品牌色和图标允许保留在前端，但必须集中在单一品牌目录。

### 2.3 允许保留的平台判断

- 连接导入时的平台别名规范化。
- 连接、SSE 事件与当前页面上下文的身份匹配。
- 平台品牌图标和颜色选择。
- Provider/策略注册表内部的平台分派。

以上判断不得影响操作是否支持、任务是否成功、是否需要停机或参数如何拼装。

## 3. 统一能力契约

API 提供统一的平台描述：

```ts
interface ProviderDescriptor {
  type: ProviderType;
  label: string;
  defaultPort: number;
  networkInterfaceLabel: string;
  capabilities: {
    inventory: boolean;
    isoLibrary: boolean;
    vmCreate: OperationCapability;
    vmRename: RenameCapability;
    vmResize: ResizeCapability;
    vmConsole: OperationCapability;
    provisioningNetworkProbe: OperationCapability;
  };
}

interface OperationCapability {
  supported: boolean;
  reasonCode?: string;
  message?: string;
}
```

前端按钮只读取能力描述。Provider 未实现某项能力时，API 返回稳定原因码，不由前端按平台名称猜测。

## 4. 统一资源 DTO

### 4.1 虚拟机

`VmNode` 增加统一 `consoleRef`。VMware MOID、PVE node/vmid、XenServer UUID 由 Provider 转换后写入该字段，前端不读取 `metadata.managedObjectId`，也不拆解 `providerId`。

### 4.2 磁盘

`VmDisk` 逐步补齐：

```ts
interface VmDisk {
  id: string;
  displayName: string;
  virtualSizeBytes: number;
  canOnlineResize: boolean;
  requiresShutdown: boolean;
  allowedModes: Array<"extend" | "add">;
}
```

平台设备号仍可作为只读诊断字段返回，但 UI 不得据此推导停机条件。

## 5. 创建接口

### 5.1 目标请求

页面提交用户意图，不重复提交模板派生值：

```ts
interface ProvisionIntentRequest {
  connectionId: string;
  hostId?: string;
  environmentTemplateId: string;
  sourceId?: string;
  specId: string;
  ipPoolId: string;
  count: number;
  overrides?: Array<{
    name?: string;
    ip?: string;
    cpu?: number;
    memoryGiB?: number;
    diskGiB?: number;
    loginUsername?: string;
    password?: string;
  }>;
}
```

外部 API 确实需要完全自定义时，使用独立的 `inline` 配置对象，不得与模板 ID 同时作为两个真值来源。

### 5.2 创建计划

新增或扩展计划/预检接口，由后端返回：

```ts
interface ProvisionPlanDto {
  planId: string;
  operationSummary: string;
  items: ProvisionPlanItem[];
  issues: Array<{
    code: string;
    severity: "blocking" | "warning" | "info";
    field?: string;
    message: string;
    actionHint?: string;
  }>;
  executable: boolean;
}
```

前端禁止通过中文文案正则判断阻断级别。

## 6. 任务与就绪状态

任务 DTO 是工作流唯一真值来源：

```ts
interface ProvisionTaskVm {
  status: ProvisionTaskStatus;
  currentStep: ProvisionTaskStepKey;
  progressPercent: number;
  message: string;
  reasonCode?: string;
  readiness?: {
    state: "offline" | "network-visible" | "protocol-ready" | "ready";
    networkVisible: boolean;
    ready: boolean;
  };
  actionHints?: string[];
}
```

- 前端直接渲染 `task.steps`，不得维护另一份完整步骤列表。
- SSE、轮询和任务恢复返回同一 DTO。
- 平台探测信号由 readiness 策略解释，Controller 和前端不判断平台。

## 7. 后端策略组织

Provider Registry 负责平台实现注册；每个平台组合以下能力：

- `inventory`
- `provisioning.plan/preflight/execute`
- `provisioning.readiness`
- `networkProbe`
- `console`
- `rename`
- `resize`
- `installMedia`

HTTP Controller 只负责参数解析、连接解析、调用策略和统一错误映射。平台判断不得继续堆积在 `index.ts`。

## 8. 迁移顺序

1. 增加 Provider Descriptor 和能力 API，前端改为读取能力。
2. 补齐 `VmNode.consoleRef`、`VmDisk` 标准字段，移除前端原始字段解析。
3. 补齐任务 readiness DTO，前端直接渲染后端步骤。
4. 将 IP 池、ISO 和创建计划校验收敛到后端 typed issues。
5. 缩减创建请求，区分模板意图与外部 API inline 意图。
6. 将 `index.ts` 中的平台预检分支迁入 Provider 策略。
7. 清理重复品牌名称、默认端口和未使用的前端平台策略。

## 9. 本轮落地范围

- Provider Descriptor、统一能力类型和查询接口。
- 前端改名、扩容入口使用能力描述。
- VM 控制台使用标准 `consoleRef`，不再补造 VMware metadata。
- 磁盘返回标准显示名和停机约束。
- 任务 DTO 返回完整 readiness，并移除前端重复的工作流步骤常量。
- 创建预检增加结构化 issue 字段，为后续缩减请求提供兼容基础。

创建请求瘦身涉及外部 API 兼容，采用分阶段迁移：先停止前端自行分类和重复推导，再增加新版 intent 接口，旧请求在兼容期内由后端统一归一。

## 10. 验收标准

- Web 组件不再通过平台类型决定改名、扩容、控制台和网络探测能力。
- Web 不读取 VMware MOID、不拆 PVE VM ID、不解释 XenServer 磁盘设备号。
- 前端不通过提示文案内容判断是否阻断。
- 任务步骤、进度和 readiness 只由 API 返回。
- Provider 能力和约束有单元测试。
- API、Web 类型检查和构建通过。
- 残留 `providerType` 判断均能归类为品牌展示、身份匹配或策略注册表分派。

## 11. 本轮落地与验收结果

已落地：

- 新增 `GET /api/providers`，统一返回 XenServer、VMware、Proxmox VE 和 KVM/libvirt 的能力、默认端口、改名规则和网络术语。
- 创建、改名、扩容和控制台入口均改为消费 Provider Descriptor，不再由前端按平台名称推导能力。
- VM 控制台标识归一为 `consoleRef`；磁盘展示名、在线扩容能力、停机约束和允许模式均由 API 返回。
- 创建预检返回 `operationSummary` 和 typed `issues`，前端不再通过中文文案正则判断阻断。
- 网络探测、创建计划校验和就绪状态进入后端策略；前端直接渲染后端 `task.steps`、`readiness` 和 `actionHints`。
- ISO 空状态由 API 返回稳定原因码、用户文案和处理建议。

验收结果：

- `npm run typecheck` 通过。
- API 测试 84/84 通过，Web 测试 13/13 通过。
- `npm run build` 通过；仅有既存的 Vite chunk 体积提示。
- 浏览器只读验收 Proxmox VE：创建入口按能力启用；改名弹窗正确显示 63 字符上限、节点级重名范围和 Provider 执行语义；扩容弹窗正确显示标准磁盘名 `scsi0` 及在线扩容约束。未提交任何变更操作。
- 页面刷新后恢复 16 个连接，本轮刷新时间窗内无新增控制台错误。

仍保留的平台判断仅用于连接身份匹配、SSE 事件归属、未保存连接变更比较、环境模板过滤、品牌展示和策略注册表分派，不参与前端业务能力判定。
